## Контракт локального управления

AF_UNIX/SOCK_STREAM, один объект JSON на строку. В запросе числовой `id`, строковый `method` и объект `params`. Ответ связывается по `id`. По тому же каналу могут приходить события. Протокол наблюдался на настоящем ARM64. Отдельный загрузчик .so не потребовался. Точный состав и типы полей из Go metadata зафиксированы в [contract-v1.json](contract-v1.json).

| Вызов | Проверка |
| --- | --- |
| `hello` с `{"protocolVersion":1}` | Вернул `protocolVersion:1` и указанную выше строку версии. |
| `status` | До запуска профиля `state=0`. Сразу после start получено `state=1, connected_since=0`. В proxy-режиме возвращён фактический `proxy_port=2080`. Код состояния сам по себе не доказывает выход через Sota. |
| `start` | Два поля-строки `configuration`, `localOptionsJson`, каждое содержит JSON. Протестированы один искусственный direct outbound и два разных входа, proxy и TUN/gVisor. В раннем опыте при запрошенном `proxy_port=18923` демон сообщил 2080. Порт для теста берётся из ответа. |
| `stop` | Пустой успешный ответ, следующий status вернул 0. Завершение отдельного процесса проверено также сигналами SIGTERM и SIGKILL. |
| Дополнительные операции | Статически видны CheckConfig, Forget, SetFileLogging, структуры событий. Само наличие внутреннего Go-метода не устанавливает имя IPC-вызова и его семантику. |

Совпадение отдельных заголовков/путей с Dart не устанавливает актуальность адресов, подписи и успешность запроса. Существующий скрипт не запускался, ранее созданный HWID не использовался. Включать его автоматически в CI с секретом преждевременно.

## Транзит и пределы результата

Внутри нового gateway netns созданы два veth с отдельными peer namespaces. Из клиентского namespace проверены TCP echo, UDP echo, DNS-запрос с проверкой transaction ID и ожидаемой A-записи. Маршрут с iif lan использует отдельную таблицу с TUN и резервным blackhole. Обратный маршрут к клиенту и исходящие соединения UID движка используют main. Цепочка inet forward пропускает только IPv4 между клиентом и TUN. Дополнительное право CAP_NET_RAW понадобилось в испытанном окружении для UDP. Без него ядро сообщило EPERM при открытии UDP-сокета. Воспроизводимый стенд находится в tools/offline_smoke.py и tools/transit_fixture.py.

На стороне «WAN» работал собственный тестовый сервер. TCP/UDP/DNS прошли, после stop и отдельно после SIGKILL были заблокированы. Сам шлюз достигал IPv6-эхо-сервера, для клиента IPv6 оставался закрытым. У клиентского namespace отсутствовал внешний интерфейс. Эти результаты относятся к Linux-стенду. WAN-сбой с реальным VPN, egress Sota, fail-closed самого RouterOS при потере всего контейнера, FastTrack, MTU/MSS и производительность остаются открытыми.

## Платформы и обновления

ARM64-стенд, Ubuntu 24.04.1 LTS ARM64, ядро 6.1.0-1025-rockchip, RAM 15 GiB, на корневом разделе свободно 94 GiB при инвентаризации. /dev/net/tun доступен. Docker CLI установлен, сокет docker.sock отсутствует. Работают containerd и runc. Стенд использует временные namespace и runc со своим runtime-каталогом. Основные маршруты и адреса стенда совпали до и после опыта.

OpenWrt: конкретный ARM64 kittend не зависит от динамического glibc. Остальные требования — ядро, TUN, netlink, capabilities, DNS, сертификаты, архитектура и права procd/firewall — нуждаются в проверке на выбранном выпуске. Для MikroTik остаются модель, RouterOS, veth/TUN и отказобезопасное правило на самом роутере.

Извлечение и OCI повторены для **одной** версии. Только несовместимая структура/контракт и подмена digest проверены отрицательными тестами. Для N → N+1 → N требуются второй реальный Linux-релиз, замер транзита до/после, отдельная резервная копия постоянного состояния/профиля и восстановление соответствующего снимка при откате. Копии снимка с ключами исключить из артефактов CI. Stable, registry и расписание не созданы.
