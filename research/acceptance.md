# Испытания лабораторного кандидата

Здесь зафиксирован первый headless-кандидат. Последующая установка веб-панели, восстановление cgroup2 для systemd и испытание зашифрованного туннеля на стенде описаны в [отчёте по веб-прототипу](gateway-web.md).

Дата — 23 ноября 2026 года, Москва. Digest OCI manifest — `sha256:9afd69255ab18ebcf854c840455f2a21dd1d7962033868205c9a7e083a6cf407`. SHA-256 доставленного OCI tar — `d31df44701a9e0e7bd26105c7311da88de02c0e62f330a334a82d0ce5b436734`. Проверка проведена на шлюзе. Архив содержит только index, oci-layout и blobs. ## Состояние шлюза

Полный нативный запуск `tools/check_candidate.sh` завершился с фактическим `native_ci_exit=77` после прохождения offline-группы.

Обычный SSH вернул `ssh: connect to host 192.168.1.88 port 22: Permission denied`. Точный вызов с require_escalated успешно вернул три строки:

```text
uid=0(root) gid=0(root) groups=0(root)
ubuntu
aarch64
```

Первая попытка выполнить `kittend --help` от root только с net/mount/PID namespace была отклонена автоматической проверкой из-за доступа к хостовой файловой системе. Разрешённый вариант использовал отдельный chroot, собственный read-only procfs, UID 65534 и no_new_privs. Установочные скрипты Sota на стенде не выполнялись.

Во время подготовки WAN-стенда runc вернул `no cgroup mount found in mountinfo`. При обследовании в mountinfo PID 1 и containerd не было cgroup2, в приватных mount namespaces systemd-resolved и systemd-networkd cgroup2 присутствовала. Исходная инвентаризация не записала mountinfo, а в журнале нужного mount unit не нашлось записей. По имеющимся данным нельзя установить момент или причину расхождения, включая возможную связь с первым WAN-тестом. Для следующих запусков все вспомогательные процессы изолированы в новом рекурсивно private mount namespace. При необходимости cgroup2 монтируется только в нём. Системное монтирование не восстанавливалось. SSH и containerd показывали active, проверенные интерфейсы и маршруты хоста совпали с исходными. Это не полная проверка здоровья системных служб.
