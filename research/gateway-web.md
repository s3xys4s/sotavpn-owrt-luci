# Веб-прототип на шлюзе

23 ноября 2026 года, Москва. Выпуск `gateway-1df3e873` запущен на Ubuntu ARM64. Шлюз с оригинальным `kittend` из Sota Connect 1.8.11+1892 и веб-панель работают в двух службах systemd. Проверка через тестовый зашифрованный сервер прошла. На действующей подписке прошли режимы VLESS, Hysteria2 и «Авто».

## Доступ и проверка

1. Открыть [веб-панель](http://192.168.1.88:8080/). Страница и RPC доступны по HTTP без пароля.
2. Открыть «Настроить доступ». Ввести ключ и запросить серверы или импортировать JSON с одним VPN-выходом или группой `urltest`. Шлюз использует собственный постоянный идентификатор. При первом обращении провайдер может учесть его как новое устройство.
3. Выбрать сервер или импортированный профиль, затем режим «Авто» либо протокол. Нажать «Подключить» и «Проверить IP». Для смены протокола отключить текущий туннель. Поле «Клиент через TUN» заполняется после успешного внешнего HTTPS-запроса отдельного клиента.

## Что удалось восстановить из Flutter

В AOT-библиотеке `libapp.so` Linux ARM64 найдены пути `/api/v1/public/subscription/profile`, `/api/v1/public/connection/list`, `/api/v1/public/connection/connect`, `/api/v1/public/connection/disconnect`, заголовки `X-Access-Key` и `X-HWID`, имена `gate_id`, `shortname` и `configuration`. В бинарнике есть также компоненты подписи запросов и проверки сертификатов. Их применимость к этим четырём операциям остаётся открытой.

Штатный Flutter-клиент запущен без ключа в отдельном chroot и сетевом пространстве с Xvfb. Локальный DNS отвечал NXDOMAIN и записывал только запрашиваемые имена. Процесс открыл окно, запросил `meowcon.net`, `sotacats.com` и адреса загрузки начальной конфигурации. Отдельные GET-запросы по HTTPS без ключа к четырём путям на `meowcon.net` дали HTTP 400 с сообщением о требуемом `X-Access-Key`. На втором домене проверен путь списка серверов. [Сценарий наблюдения за клиентом](../tools/flutter_reference.sh)

Панель обращается к `https://meowcon.net/api/v1/public` по HTTPS. На стенде подтверждены получение списка серверов, выдача профиля выбранного сервера и закрытие сессии при отключении. Для этих операций с данным сервером и ключом достаточно штатных заголовков панели. При ошибке подготовки профиля панель закрывает запрос сессии, при следующей попытке проверяет оставшуюся незакрытую сессию. [Адаптер провайдера](../cmd/panel/provider.go)

Импорт принимает объект с `outbounds` или ответ с полем `configuration`. В режиме «Авто» шлюз сохраняет группу `urltest`, её настройки и оба VPN-выхода в порядке провайдера. При выборе VLESS или Hysteria2 шлюз передаёт ядру только выходы указанного протокола. Отсутствующий протокол даёт явную ошибку. Режим full принимает также профили с одним выходом. Прямой выход внутри группы и вложенные цепочки отклоняются. [Проверка и подготовка профиля](../internal/profile/full.go)

## Что измеряет кнопка

Служба выполняет два запроса к `https://1.1.1.1/cdn-cgi/trace` и принимает публичный IPv4 из ответа. Для прямого запроса проверяет маршрут служебного UID через интерфейс `wan`. Для запроса отдельного клиента проверяет маршрут пересылаемого пакета с `lan` через `sotatest0`. При обрыве активного туннеля поле показывает «Недоступен», при отключении — «Выключен». Время отображается по завершении измерения. Если оба пути дали один IP, интерфейс явно сообщает об этом.

| Проверка на финальной сборке | Результат |
| --- | --- |
| Доступ из LAN | Запрос страницы без учётных данных вернул HTTP 200. JSON-RPC с браузерным Origin вернул результат проверки прямого WAN. Старый порт 8443 закрыт. |
| Запрос от отдельного клиента | HTTP-панель → подключение импортированного тестового профиля → TUN оригинального ядра → Shadowsocks AEAD → внешний сервис вернул публичный IPv4. Тестовая копия использовала отдельное состояние и временный тестовый сервер. |
| Остановка тестового сервера при активном ядре | Прямой IPv4 по-прежнему получен. Через TUN ответ отсутствовал. |
| Явное отключение | При следующем измерении состояние TUN — `disconnected`, адрес отсутствует. |
| Действующая подписка, один выбранный сервер | VLESS → отключение → Hysteria2 → отключение → «Авто». В каждом режиме ядро достигло состояния 2, внешний IPv4 клиента через TUN отличался от прямого WAN. Последний замер повторён через HTTP-панель с отдельного компьютера. |
| Сборка и интерфейс | Тесты пакетов проекта прошли на целевой Linux ARM64. В Chrome проверены форма, выбор сервера, кнопки и отображение результата на ширинах 375 и 1200 пикселей с моделируемым RPC. |

На рабочей службе каталог `/dev/net` явно монтируется с правами 0755. При отключении брокер ждёт исчезновения предыдущего TUN. На стенде ядро освобождало интерфейс примерно через 3,6 с после перехода в idle. Быстрое повторное подключение проверено отдельным тестом и на живых сессиях. Принадлежность публичного IP независимо от провайдера не сверялась. TCP, UDP, DNS и блокировка IPv6 проверялись отдельно на лабораторном образе. [Предыдущие испытания](acceptance.md)

## Установка и повторная проверка

Работающий выпуск находится в `/opt/sota-lab/releases/gateway-1df3e873`, активный путь — `/opt/sota-lab/current`. Digest OCI с ядром — `sha256:1150396a551fc8e3a6b3781d296f6315e10de625f49c742be53e4f9c62783088`. SHA-256 отдельного бинарника панели — `9642fe02fa2ef133be21fe967488a9879ee832d978c082b124a9dd449d14cdd1`. SHA-256 upstream — `bde34f88ab454f2f8d7ee2c24dba2eff94da4371969d05f5c0b45faf3f824af8`. [Манифест OCI](gateway-web-oci.json)

Команды сборки выполнять из корня проекта на Ubuntu ARM64, с Go 1.27.4 и предварительно извлечённым `build/arm64`. Сборщику нужны nft и системные сертификаты той же ревизии, стенду — runc, slirp4netns, iproute2, util-linux, Python 3, работающие cgroup2 и TUN.

```sh
export CGO_ENABLED=0 GOTOOLCHAIN=local
go test -count=1 ./cmd/... ./internal/...
go build -trimpath -ldflags '-s -w -buildid=' -o build/gateway-linux ./cmd/gateway
go build -trimpath -ldflags '-s -w -buildid=' -o build/panel ./cmd/panel
base=sha256:956429dbc2ad5ff8e10c2036772c37f86c7058fb4f55eefd63c9888e2a55f64c
mkdir -p build
stage=$(mktemp -d "$PWD/build/gateway-XXXXXXXX")
python3 tools/build_oci.py build/arm64 build/gateway-linux "$stage/image" --wrapper-source-sha "$(python3 tools/wrapper_id.py)" --base-digest "$base"
install -m 0755 build/panel "$stage/panel"
cp -R tools deploy "$stage/"
sudo install -d -m 0755 /opt/sota-lab/releases
r=/opt/sota-lab/releases/$(basename "$stage")
sudo mkdir -m 0755 "$r"
sudo cp -R "$stage/." "$r/"
sudo chmod 0755 "$r"
sudo sh "$r/deploy/linux/install.sh" "$r" 192.168.1.88
```

Установщик включает автозапуск и перезапускает обе службы. Для обновления только веб-панели служит аргумент `--panel-only`. Он перезапускает одну службу, сохраняя работающий туннель. Настройки, ключ подписки, импортированный профиль и идентификатор устройства хранятся в закрытом каталоге `/var/lib/sota-panel`. Параметры служб — в `/etc/sota-panel`. Рантайм размещает рабочий профиль в tmpfs и после своего запуска ожидает явного подключения. Полный цикл отката состояния между версиями upstream пока предстоит испытать.

HTTP служит только для управления. В `/etc/sota-panel/service.env` параметры `SOTA_API_ENABLED`, `SOTA_WEB_ENABLED` и `SOTA_HTTP_LISTEN` управляют внешней службой. При false/false она завершает работу без listener, при true/false доступен только JSON-RPC по HTTP, для включения UI нужен API. Здесь же можно указать один из `SOTA_ACCESS_KEY` или `SOTA_ACCESS_KEY_FILE`. Значение из окружения блокирует редактирование ключа в UI. Корневой брокер принимает фиксированный набор команд через приватный Unix-сокет. HTTP-процесс работает от пользователя `sota-panel`.

На стенде можно повторить проверки. Второй сценарий использует извлечённый тестовый `ss-server` в отдельном стенде.

```sh
cd /opt/sota-lab/current
sudo python3 tools/panel_smoke.py
sudo python3 tools/panel_tunnel_test.py image panel /var/tmp/sota-test-tools/rootfs
systemctl is-active sota-lab-runtime sota-lab-panel ssh containerd
```

Для запуска служб восстановлено монтирование cgroup2 в `/sys/fs/cgroup` в пространстве PID 1. После этого systemd смог запустить временную службу и обе службы шлюза. На момент проверки основной маршрут стенда проходил через `192.168.1.1 dev end1`. Пересылка домашнего трафика на этот стенд, перезагрузка стенда, RouterOS и OpenWrt остаются отдельными испытаниями.
