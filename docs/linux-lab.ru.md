# Linux-стенд Sota Gateway

В образе работают оригинальный статический `kittend` и собственный Go-контроллер. Оба запускаются без Flutter. Стадия готовности и граница между desktop-клиентом и Go описаны в [исследовании](../research/client-1.8.11.md). Кандидат рассчитан на изолированный Linux-стенд. Развёртывание на домашнем роутере требует отдельной проверки сетевых возможностей и политики отказа.

## OpenWrt и LuCI

Гостевой маршрутизатор OpenWrt 25.12.6 управляет исходным ARM64-ядром через procd. Через LuCI можно выбрать сервер и протокол, настроить DNS и маршрутизацию по IPv4, CIDR и доменным спискам, сравнить внешние IP и посмотреть события. [Сборка, установка и проверки](../openwrt/README.md)

## Веб-панель Linux

По умолчанию панель управляет OpenWrt. Пункт «Linux-стенд» открывает прежний изолированный шлюз. Доступны [LuCI на порту 8081](http://192.168.1.88:8081/cgi-bin/luci/admin/services/sota/status) и [основная панель в локальной сети](http://192.168.1.88:8080/). Страница и JSON-RPC открываются по HTTP без пароля. Управление доступно каждому, кто может подключиться к этому адресу.

Флаги **RU / EN** в шапке переключают язык основной панели. Браузер запоминает выбор. Поле **HWID устройства** на странице подключения показывает действующий идентификатор выбранного шлюза. В LuCI язык задаётся в системных настройках OpenWrt.

В «Настроить доступ» можно ввести ключ подписки или импортировать JSON-профиль. Выберите сервер и протокол. В режиме «Авто» оригинальное ядро использует группу `urltest` из профиля Sota. Ручные режимы VLESS и Hysteria2 используют только выбранный транспорт. Нажмите «Подключить», затем «Проверить IP». Все три режима проверены на действующей подписке с отдельного клиента за TUN. Для смены режима отключите текущее соединение.

Две службы systemd запускают изолированный шлюз и HTTP-панель. Настройки панели и постоянный идентификатор устройства хранятся отдельно от OCI-образа. Условия пересборки, настройки служб, результаты и ограничения описаны в [отчёте по шлюзу](../research/gateway-web.md).

## Извлечение

Команды выполнять из каталога проекта. На стенде использованы Python 3.12 и Go 1.27.4. Для статического извлечения достаточно Python 3.9+. Все выходные каталоги должны быть новыми. Сценарии не устанавливают .deb и не запускают maintainer scripts.

```sh
python3 tools/candidate.py v1.8.11 '1.8.11+1892' arm64 build/arm64
python3 tools/candidate.py v1.8.11 '1.8.11+1892' amd64 build/amd64
python3 tools/test_extraction.py cache/44ec209c690ed718879486341529dd89e01b3783790b306c2b5cfe7681ecedbd.deb
```

Для уже скачанного архива `tools/extract.py --help` показывает параметры версии, архитектуры, официального URL и ожидаемого SHA-256. `candidate.py` получает digest из Release API. Можно указать официальный CDN через `--source`. Извлечение закрывается при смене состава или режимов файлов, unit, структуры Go IPC, ELF-архитектуры либо типа линковки. Проверка структуры имеет ложные срабатывания при косметических изменениях upstream. Новый контракт утверждают после разбора различий и динамической проверки.

## Проверка ядра на Linux

На одноразовом ARM64-стенде нужны `unshare`, `nsenter`, `ip`, `nft`, `mount` и поддержка TUN. Подготовка изолированных пространств требует root. Сам upstream работает с UID 65534. Вариант TUN использует CAP_NET_ADMIN и CAP_NET_RAW в закрытой топологии. Вариант proxy обходится без них.

```sh
core_sha=bde34f88ab454f2f8d7ee2c24dba2eff94da4371969d05f5c0b45faf3f824af8
sudo python3 tools/offline_smoke.py build/arm64/kittend "$core_sha"
sudo python3 tools/offline_smoke.py build/arm64/kittend "$core_sha" --tun
sudo python3 tools/offline_smoke.py build/arm64/kittend "$core_sha" --tun --crash
```

В последнем опыте ядро получает SIGKILL при активном тестовом трафике. Ожидаются успешные TCP, UDP, DNS до падения и отказ всех трёх после падения. Режим IPv6 лаборатории — явная блокировка транзита. При доступности IPv6 сам шлюз достигает контрольного сервера.

## Сборка и проверки кандидата

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -trimpath -ldflags '-s -w -buildid=' -o build/gateway-arm64 ./cmd/gateway
base=sha256:956429dbc2ad5ff8e10c2036772c37f86c7058fb4f55eefd63c9888e2a55f64c
python3 tools/build_oci.py build/arm64 build/gateway-arm64 build/oci --wrapper-source-sha "$(python3 tools/wrapper_id.py)" --base-digest "$base"
sudo python3 tools/oci_smoke.py build/oci
sudo python3 tools/live_accept.py build/oci --preflight --check-wan
```

Сборка runtime использует нативный Ubuntu ARM64: nft из дистрибутива, его конкретные ELF-зависимости и набор корней Mozilla. Все файлы базы захешированы в [манифесте](../research/arm64-oci.json). Другая ревизия библиотек или CA изменит digest. Для исследования новой базы есть `--inspect-new-base`. В сценарии проверки используется зафиксированный digest. Каталог `build/oci` имеет формат OCI Image Layout. Внешний registry для сборки не требуется.

Полный независимый от хостинга сценарий для чистого ARM64 build runner с Go в PATH:

```sh
sh tools/check_candidate.sh v1.8.11 '1.8.11+1892' /tmp/sota-candidate-new "$base"
```

Сценарий запускается с правами создания изолированных стендов. Без тестового профиля и ожидаемого VPN-выхода он завершится кодом **77** после локальных тестов. При несовместимости, сетевом сбое или отказе провайдера результат также не переводится в stable. Этот сценарий принимает готовый профиль. Экспериментальный обмен по ключу реализован в отдельной службе панели. Поле `dynamic_compatibility` в манифесте отражает момент упаковки. Запуски после сборки привязаны к digest в [журнале испытаний первого образа](../research/acceptance.md) и [отчёте по веб-панели](../research/gateway-web.md). Манифесты первых лабораторных сборок содержат SHA-256 исходников обёртки.

## CLI и настройки процесса gateway внутри OCI

Одна программа поддерживает `gateway run`, `check`, `status`, `diagnostics`, `connect`, `disconnect` и `version`. Управляющий процесс открывает Unix-сокет в приватном каталоге состояния. `status` отдельно возвращает жизнь контроллера, наличие дочернего процесса, ответ на IPC, числовое состояние ядра и статус проверки трафика. Внешний тест проверяет egress отдельно. Встроенная проверка трафика и мониторинг долгой сессии ещё не реализованы.

Конфигурация — JSON-объект. Имена полей совпадают с суффиксами env, например `{"AUTOCONNECT":false,"API_ENABLED":false,"WEB_ENABLED":false}`. Порядок — defaults, затем файл по абсолютному пути `SOTA_CONFIG_FILE`, затем env. Команда `check` выводит происхождение параметров и скрывает значения. По умолчанию сервис запускает демон в idle и открывает только Unix-сокеты.

| Настройка | Поведение отдельного процесса `gateway` |
| --- | --- |
| `SOTA_STATE_DIR` | По умолчанию /var/lib/sota-gateway, отдельный приватный том для постоянных данных. Каталоги run и core раздельны. |
| `SOTA_PROFILE_FILE` | Приватный файл с `outbounds`. Поддерживаются один VPN-выход или группа `urltest` с именованными VPN-выходами. Контроллер проверяет доступ к файлу, структуру и ссылки группы. |
| `SOTA_AUTOCONNECT` | При true необходим валидный профиль и защитная цепочка испытанного стенда. Отказ start прекращает попытки активации. Для мёртвого процесса предусмотрено до трёх повторных запусков с задержками 1, 2, 4 секунды. |
| `SOTA_ROUTE_MODE` | Кандидат поддерживает только лабораторный full. За защитные маршруты, veth и обратный путь отвечает стенд. |
| `SOTA_API_ENABLED`, `SOTA_WEB_ENABLED`, `SOTA_HTTP_LISTEN` | В OCI используется false/false. Процесс gateway отклоняет включение HTTP. На шлюзе эти параметры для HTTP задаются в окружении службы панели. |
| `SOTA_ACCESS_KEY`, `SOTA_ACCESS_KEY_FILE` | Одновременное присутствие — ошибка, включая конфликт между файлом и env. По отдельности возвращается явное сообщение о недоступности выдачи профиля по ключу. |
| `SOTA_SERVER`, `SOTA_COUNTRY`, `SOTA_LOG_LEVEL` | Явный выбор страны или сервера отклоняется. В лабораторной сборке доступен уровень info. |

## Живой тест

Если есть настоящий профиль от провайдера, передать стенду только путь к приватному файлу. Целевой выход для сильной проверки определяется независимо, например из наблюдения с тем же выбранным сервером в официальном клиенте. Ключ подписки и содержимое профиля не помещать в команду или переписку.

```sh
sudo python3 tools/live_accept.py build/oci --profile /private/provider.json --expect-egress "$EXPECTED_VPN_IPV4_OR_PREFIX"
```

Контроллер, выход WAN через slirp4netns и тестовый клиент изолированы. В этом опыте контроллер допускает испытанную цепочку nft для интерфейсов `lan` и `sotatest0`. Хостовые маршруты для запуска не требуются. Проверяются внешний адрес из HTTPS, независимый UDP/STUN и DNS. При отсутствии ожидаемого диапазона возможен замер с `--profile`: результат без подтверждения принадлежности egress возвращает 77. Три живых подключения через веб-панель с проверкой IPv4 по HTTPS описаны в [отчёте по шлюзу](../research/gateway-web.md). Протокол проверки использует [Cloudflare trace](https://developers.cloudflare.com/fundamentals/reference/cdn-cgi-endpoint/) и [публичный STUN Cloudflare](https://developers.cloudflare.com/realtime/turn/).

Для интеграционного CI нужны монтируемый секрет `SOTA_CI_PROFILE_FILE` и `SOTA_CI_EXPECT_EGRESS`. Текущий скрипт не продвигает и не публикует образы. После появления интеграции по ключу секрет подписки должен оставаться у адаптера регистрации, отдельно от логов, manifest и резервных копий общего назначения.
