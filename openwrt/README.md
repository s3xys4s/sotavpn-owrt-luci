# Sota Gateway для OpenWrt

Прототип испытан на OpenWrt 25.12.6, цель `armsr/armv8`, архитектура пакета `aarch64_generic`. На стенде один гость KVM служит маршрутизатором, второй получает от него адрес, маршрут и DNS через DHCP. Из сети 192.168.1.0/24 доступны [LuCI](http://192.168.1.88:8081/cgi-bin/luci/admin/services/sota/status) и [основная панель](http://192.168.1.88:8080/). По умолчанию обе управляют одним гостевым маршрутизатором. Переключатель в основной панели также открывает прежний Linux-стенд. На стенде используется штатный вход LuCI с именем `root` и пустым паролем. [Запуск виртуальных машин](../tools/openwrt_vm.sh)

LuCI использует язык из **System → System → Language and Style**. При выборе **Auto** LuCI учитывает язык браузера. Для русского интерфейса LuCI установите пакет `luci-i18n-base-ru`. В отдельной панели флаги **RU / EN** переключают язык сразу и сохраняют выбор в текущем браузере.

Для Routerich AX3000 доступны отдельные комплекты для OpenWrt 24.10 и 25.12. [Инструкция для Routerich AX3000](ROUTERICH.md)

## Установка на совместимую тестовую систему

Скопировать два APK и открытый ключ из `build/openwrt` в `/tmp` гостевой OpenWrt. На маршрутизаторе с настроенными репозиториями своего релиза выполнить

```sh
cp /tmp/sota-lab.pem /etc/apk/keys/sota-lab.pem
apk verify /tmp/sota-gateway-0.1.0-r19.apk /tmp/luci-app-sota-0.1.0-r15.apk
apk add /tmp/sota-gateway-0.1.0-r19.apk /tmp/luci-app-sota-0.1.0-r15.apk
/etc/init.d/sota enable
/etc/init.d/sota start
/etc/init.d/firewall reload
/etc/init.d/rpcd restart
```

1. Открыть **Services → Sota Gateway → Сеть и DNS**. Выбрать сетевое устройство защищаемой LAN. На тестовом роутере это `eth0`, в типовой мостовой конфигурации — `br-lan`. Для стенда с программным или аппаратным flow offloading сначала отключить разгрузку во вкладке Firewall.
2. Указать DNS для внешних запросов и отметить «Включить правила маршрутизации». При стандартном режиме до подключения к VPN прямой выход остаётся для WAN-исключений. Если поле «Устройства, для которых действуют правила» пустое, правила охватывают весь выбранный интерфейс.
3. Открыть **Подключение**, сохранить ключ, выбрать сервер и протокол. «Авто» сохраняет выбор транспорта из профиля Sota. Вручную доступны VLESS и Hysteria2, если выбранный сервер их предоставляет. Нажать **Старт**.
4. Нажать **Проверить IP**. Два независимых HTTPS-запроса с маршрутизатора показывают внешний IPv4 прямого WAN и TUN. Виджет **Последние события** показывает до 100 событий контроллера, время, уровень и результат. Доступны фильтр и пауза. История виджета хранится в памяти до перезапуска контроллера.

Поле **HWID устройства** на странице подключения показывает идентификатор текущего шлюза из заголовка `X-HWID`. Новая установка вычисляет его по алгоритму Linux-клиента Sota Connect 1.8.11. На тестовой копии оригинального клиента проверены заголовки `X-HWID` запросов `/subscription/profile` с фиктивным ключом. Контрольные примеры включают `machine-id`, данные `os-release` и `lsb-release` и резервное имя хоста. [Тесты совместимости](../cmd/panel/hwid_linux_test.go)

Обновление сохраняет существующую регистрацию из `/etc/sota/settings.json`. Если `machine-id` отсутствует, одинаковые поля выпуска Linux могут дать одинаковый HWID на нескольких роутерах.

## Маршрутизация

Клиенты и исключения задаются IPv4-адресами или CIDR в `/etc/config/sota`. Защищённый трафик получает метку `0x534f` и использует таблицу `21519` с блокирующим запасным маршрутом. При аварии ядра таблица блокирует назначенный в VPN трафик до автоматического восстановления туннеля. Кнопка **Стоп** снимает правила и возвращает обычный WAN. **Старт** сохраняет выбранное подключение для восстановления после перезагрузки, **Перезапуск** переподключает его. Для исключённых назначений и клиентов используется обычная маршрутизация OpenWrt.

Классический DNS защищённых клиентов по UDP и TCP на порту 53 перехватывает отдельный экземпляр dnsmasq. Его внешние запросы идут через TUN, локальный DNS-домен обслуживает системный dnsmasq. Для запуска VPN и обращения к API используется системный DNS OpenWrt через WAN. При заполненном поле **DNS over HTTPS** внешний клиентский DNS идёт через VPN по HTTPS, а поле **DNS через VPN** используется для разрешения имени DoH-сервера. Пересылка IPv6 и доступ к локальному DNS через IPv6 блокируются на всём защищённом интерфейсе. 

### Правила назначения

В разделе **Списки маршрутизации** поле **Ручные правила** принимает IPv4, CIDR и домены по одному на строку. CIDR с адресом хоста приводится к адресу сети, например `192.168.1.1/24` охватывает `192.168.1.0/24`.

При установке и первом обновлении добавляются обычные текстовые ссылки для YouTube, Discord, Meta (Facebook, Messenger, WhatsApp), Instagram и Twitter / X. У каждого сервиса две выгрузки OpenCCK — доменные имена и IPv4/CIDR. Параметр **Куда направлять трафик** действует на все эти списки. Вручную изменённые и удалённые строки сохраняются. Вернуть конкретный встроенный источник можно ссылкой под редактором. [Каталог OpenCCK](https://iplist.opencck.org/)

Раздел **Исключения** использует те же форматы ручных правил, ссылок и файлов. Совпадения идут через WAN при любом направлении основного списка. Там по умолчанию находится обычный файл **Российские сайты (Sota Connect).txt**. Первоисточники — файлы установленного клиента `rule_sets/ru/geosite.srs` и `geoip.srs`. Их SHA-1 совпали с манифестом приложения: `0bdee27cb1d29cd3e951b1e3547f95664c6cd391` и `f6c28b283a8c3b1f02ed269a32a5682c4cc5f764`. Штатный `sing-box rule-set decompile` извлёк 143 доменных правила и 8 580 IPv4-подсетей. Суффиксы, охватывающие и имя, и поддомены, записаны двумя строками вида `example.com` и `*.example.com`. Ещё 2 171 IPv6-подсеть относится к трафику, пересылку которого шлюз блокирует. После удаления доступна ссылка возврата встроенного файла. Пользовательские списки в меню возврата не попадают.

В блоке **Списки по ссылкам** кнопка **+ Добавить список** создаёт строку для URL. Шлюз скачивает новый источник по HTTP или HTTPS при сохранении, затем проверяет ссылки без открытой панели. Первый запуск проверки после старта службы — через минуту. По умолчанию интервал составляет 360 минут. Поле **Интервал обновления ссылок, мин** принимает значения от 1 до 10080. При сбое загрузки или разбора сохраняется последняя рабочая копия конкретного источника, а остальные обновляются. Изменения и ошибки видны в журнале.

В блоке **Списки из файлов** кнопка **+ Добавить файл** позволяет выбрать один или несколько файлов. У каждого файла есть собственная строка с именем и кнопкой **−**. Файлы хранятся на шлюзе и после перезапуска. Удаление файла или ссылки вступает в силу после нажатия **Применить правила**. Ручные правила, файлы и ссылки объединяются. Правило действует, пока присутствует хотя бы в одном источнике. Импорты, которые старая версия добавила в ручное поле, остаются в нём.

Лимит ручных правил — 256 КиБ. В каждой группе поддерживаются до 42 ссылок по 2 МиБ, до 10 МиБ суммарно. Для локальных файлов лимит составляет 32 файла по 2 МиБ, до 8 МиБ суммарно. Если настройки изменили в другой панели, нажмите **Прочитать сохранённые настройки** перед редактированием.


| Запись | Действие |
| --- | --- |
| `198.51.100.7` или `203.0.113.0/24` | IPv4-адрес или подсеть |
| `+.example.org`, `DOMAIN-SUFFIX,example.org`, `\|\|example.org^` | Домен и его поддомены |
| `example.org` или `DOMAIN,api.example.org` | Только указанное имя |
| `*.example.org` | Поддомены |
| `IP-CIDR,203.0.113.0/24,no-resolve` | Подсеть в синтаксисе Mihomo/Clash |

Для файлов подходят обычный текст и YAML-последовательность под ключом `payload:` с перечисленными типами правил. Пустые строки и комментарии с `#` пропускаются. В режиме «Список через VPN» указанные назначения используют TUN, остальные идут через WAN. В режиме «Список через WAN» порядок обратный. Поле «Всегда через WAN» имеет приоритет. Оба режима действуют для выбранных клиентов. [Синтаксис rule-provider](https://wiki.metacubex.one/config/rule-providers/content/)

При наличии доменных правил SmartDNS принимает клиентский DNS и добавляет IPv4 из ответов в nftables на ограниченное время. Внешние запросы он передаёт отдельному dnsmasq с маршрутом через VPN. SmartDNS сохраняет клиентский порт 1053 и при пустом списке. Выделенный dnsmasq постоянно слушает на 127.0.0.1:1054. Для проверки после изменения правил повторите DNS-запрос через шлюз. При собственном DoH/DoT клиента шлюз может не увидеть ответ. На общем IP CDN сетевое правило затрагивает все соединения к этому адресу. [Настройки nftset в SmartDNS](https://github.com/pymumu/smartdns/blob/Release46.1/etc/smartdns/smartdns.conf)

### Публикация стенда

На хосте сокет `sota-luci-lan.socket` привязан к `192.168.1.88:8081` на `end1` и пропускает источники из `192.168.1.0/24`. Он передаёт TCP на гостевой HTTP через `127.0.0.1:18081`. Основная панель использует приватный SSH-канал `sota-openwrt-rpc.service`. Для него на госте включена опция UCI `sota.main.local_rpc=1`, на хосте службе панели задано `SOTA_OPENWRT_BRIDGE=1`. Старый API Linux сохраняется по `/rpc`. [Файлы systemd для стенда](../deploy/linux/lab/)


## Сборка

Нужны исходный статический ARM64 `kittend` из Sota Connect 1.8.11+1892 в `build/arm64/kittend`, Go и распакованный Linux SDK нужного релиза. Для этого стенда использовался [официальный SDK armsr/armv8](https://downloads.openwrt.org/releases/25.12.6/targets/armsr/armv8/). В SDK должны быть подготовлены feeds, конфигурация и ключи сборки. Для перевода меню требуется штатная утилита `staging_dir/host/bin/po2lmo` из `luci-base/host`. Из корня проекта выполнить

```sh
CGO_ENABLED=0 GOOS=linux GOARCH=arm64 go build -tags=luci_only -trimpath -ldflags='-s -w' -o build/openwrt-controller-arm64 ./cmd/panel
sh tools/build_openwrt.sh "$SDK"
```

Скрипт проверяет SHA-256 ядра и метку сборки контроллера. SDK 25.12 выпускает подписанные APK и открытый ключ, SDK 24.10 выпускает IPK. Второй аргумент скрипта задаёт выходной каталог, по умолчанию `build/openwrt`. Ключ подписки хранится отдельно в `/etc/sota`.

## Проверки

С отдельного LAN-клиента HTTPS и UDP/STUN показали одинаковый внешний IPv4 VPN, отличный от исходного WAN. Проверены DNS, добавление и удаление исключения назначения /32, исключение клиента из защищённой группы и перечитывание firewall4. При обычном отключении и аварийном завершении ядра проверены три новых запроса — HTTPS, UDP/STUN и DNS. Проверка браузером охватила вход в LuCI, состояние подписки, список серверов, IP-диагностику, журнал и форму сети. В браузере последовательно подключены VLESS, Hysteria2 и «Авто». Во всех трёх случаях виджет показал разные адреса WAN и TUN. На защищённой LAN также проверена блокировка DNS по link-local IPv6 при доступном IPv6-адресе маршрутизатора. [Сетевые пробы](../tools/egress_probe.py)

Производительность физического роутера, длительные игровые и голосовые сессии и полный паритет с настольным приложением ещё требуют отдельных испытаний.
